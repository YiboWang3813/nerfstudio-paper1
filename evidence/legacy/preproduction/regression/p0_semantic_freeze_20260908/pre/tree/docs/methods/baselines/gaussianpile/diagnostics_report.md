# GaussianPile anomaly report

Context: synthetic_liver 6-method production comparison, 30k iterations, best checkpoint selected by held-out PSNR.

## 2026-06-08 resolution

Status: resolved for the production comparison protocol.

The anomaly described below came from superseded GaussianPile comparison runs.
The accepted rerun was the `_gpile0608_stable5` batch. It fixes the black final
artifact problem by restoring the saved best Gaussian container for final
visualization/manifest artifacts, and by making the comparison summary consume
the restored evaluation row when multiple evaluations share the same step.

All six accepted sweeps have `final pred_all_black_frac = 0.0`. After
validation, the output root was cleaned: superseded GaussianPile folders were
deleted, stale 6-method montage PNGs were removed, and the accepted rerun
folders were renamed to the canonical no-suffix experiment names generated by
the comparison scripts. See:

```text
outputs/production/comparisons/synthetic_liver_6method_best/synthetic_liver_6method_best_results.tsv
docs/methods/baselines/gaussianpile/reproduction_results.md
```

Remaining caveat: `r3` is still a low-quality GaussianPile case
(`best/final PSNR 22.5711`) compared with other sweeps. This is no longer a
black-screen artifact issue, but it should be treated as a method/configuration
weakness of the current baseline.

## Summary

GaussianPile looks abnormal in this comparison. It consistently prunes much more aggressively than the other GS methods, ending with only about 0.36M-0.42M Gaussians from a 1M initialization, while ultragauss/ours/ultragray generally retain about 0.78M-1.03M. Its perceptual metrics are also weak: mean LPIPS is 0.4926, much worse than ours 0.1901, ultragauss 0.2689, and ultragray 0.3088.

The clearest failure is `r1`: GaussianPile's best checkpoint is at 10k with PSNR 24.5109, but the final 30k checkpoint collapses to PSNR 14.1587. The saved `vis/` predictions for `r1` are all black for item5/item10/item15/item20/item25: grayscale mean 0.0, std 0.0, max 0.0. This means the numeric table is using the best checkpoint, but the visual folder is showing the final collapsed output.

## Likely issues to investigate

1. Density control appears too prune-heavy for this setup. Early pruning removes hundreds of thousands of points, and later `Split`/`Clone` are often zero while pruning continues, leaving GaussianPile far below the intended 1M budget.
2. The `r1` run has a hard collapse after 10k. This suggests either unstable opacity/intensity/scale behavior, a bad pruning threshold/schedule, or a renderer/output normalization failure in later checkpoints.
3. The comparison visual protocol reads `vis/`, which currently reflects the final evaluation output rather than the best-checkpoint output. For GaussianPile r1, this exposes the final collapse even though the metric table uses best checkpoint.

## Recommendation for the GaussianPile agent

Debug `synthetic_liver_r1_gaussianpile_1m_30k_dc_nmax2m_best` first. Reproduce the 10k -> 15k collapse, inspect density-control decisions around that interval, and check whether rendering at 15k+ emits zero-valued predictions because all effective opacity/intensity/transmittance is killed. Also add a guard or regression test that catches all-black held-out predictions.
